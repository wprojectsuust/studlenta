# ADR-0013: Кеш публичного чтения в памяти процесса + HTTP-кеширование

- **Статус:** принято
- **Дата:** 2026-10-23

## Контекст
Большинство запросов — гости, листающие ленту, календарь и страницы событий. Ответы для
всех гостей одинаковы. Сервер маленький (1 ГБ, общий с другим продом), каждая поездка
в PostgreSQL дорога. Одна реплика API.

## Решение
1. **`TtlCache` в процессе** (`infrastructure/cache.py`, порт `ReadCache`): TTL + LRU
   (512 записей) + «один запрос на ключ» при параллельных промахах (без лавины в базу).
   Кешируются только гостевые ответы: лента (15 с), событие (30 с), категории (30 с),
   календарь (60 с). Персональное (флаги «лайкнул», избранное, кабинет) — никогда.
2. **Сброс по событию**: одобрение и снятие с публикации сразу очищают кеш — новое событие
   видно мгновенно, снятое пропадает мгновенно. Сброс во время загрузки не даёт закешировать
   устаревший результат (счётчик поколений). Лайки кеш не сбрасывают: счётчик у гостя
   догоняет за ≤ 15 с.
3. **HTTP**: гостевые GET публичных ресурсов — `Cache-Control: public, max-age=15,
   stale-while-revalidate=60` и `Vary: Authorization`; всё остальное — `private, no-store`.
4. Страница события на фронтенде уже кешируется Next (`'use cache'`, минуты) — ADR-0011.
5. **Обложки**: при загрузке сервер сохраняет не исходник, а JPEG ≤ 1600 px и превью 640 px
   (`…-640.jpg`), с учётом EXIF-поворота и без метаданных (GPS с телефона не утекает).
   Лента берёт превью через `srcset`, первые две карточки грузятся сразу (`fetchpriority`).
   Замер на проде: обложка мини-футбола 880 КБ → 493 КБ (страница события) и 73 КБ (лента);
   восемь превью ленты вместе ~0,4 МБ вместо ~4 МБ исходников.

## Рассмотренные варианты
- **Redis** — ещё один сервис и ~30 МБ памяти ради одной реплики.
- **proxy_cache в nginx** — сложнее сбрасывать по событию, конфиг общий с соседним продом.

## Последствия
- Замер локально (300 гостевых запросов): p50 ленты 6,7 → 4,4 мс, категорий 4,5 → 3,1 мс,
  события 5,0 → 3,3 мс; на сервере выигрыш больше — запросы до базы не доходят.
- При нескольких репликах кеш станет локальным для каждой — сброс нужно будет рассылать
  (Redis pub/sub) или сократить TTL.
