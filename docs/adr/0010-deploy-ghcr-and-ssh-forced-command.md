# ADR-0010: Деплой: образ в GHCR, выкатка по SSH с принудительной командой

- **Статус:** принято
- **Дата:** 2026-10-23

## Контекст
Прод — VPS karrad.tech (1 ГБ RAM, мало диска), на нём уже работает другой сервис
(«База знаний УУНиТ») за общим nginx. Сервис публикуется по пути `karrad.tech/studlenta`.

## Решение
1. CI собирает образ в GitHub Actions и пушит в `ghcr.io/wprojectsuust/studlenta-api:<sha>` —
   на VPS ничего не собирается.
2. Деплой — SSH с отдельным ключом. В `authorized_keys` он ограничен
   `command="/opt/studlenta/deploy.sh",restrict`: ключ умеет только выкатить тег, без shell
   и проброса портов. Личные ключи в GitHub не попадают.
3. `deploy.sh` принимает тег, входит в GHCR коротким токеном джобы (через stdin), делает
   `pull` + `up -d`, ждёт health и **откатывается** на прошлый тег, если не дождался.
   Старые образы удаляет — диск маленький.
4. nginx: один `location /studlenta/` в существующем сайте karrad.tech, префикс срезается;
   приложение знает его через `STUDLENTA_ROOT_PATH` (cookie, ссылки на обложки, Swagger).
5. Postgres 16-alpine — тот же образ, что у соседнего сервиса, слои общие.
   Ограничения памяти контейнеров защищают соседний прод.
6. Секреты прода (`JWT`, пароль БД) создаются на сервере и в репозиторий не попадают.

## Последствия
- Выкатка — только из `main` и только после зелёных проверок и тестов.
- Нет blue-green: при деплое API недоступен несколько секунд.
- Отдельный поддомен потребует только DNS-записи и нового `server`-блока; код не меняется.
