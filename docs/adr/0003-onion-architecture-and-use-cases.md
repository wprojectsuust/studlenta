# ADR-0003: Onion-архитектура, отдельный use case на каждый сценарий

- **Статус:** принято
- **Дата:** 2026-10-23

## Контекст
Требование команды: архитектура onion и use case на каждый сценарий. Нужно, чтобы правила
модерации не расползлись по роутерам и SQL, и чтобы их можно было тестировать быстро.

## Решение
Четыре слоя: `domain` → `application` → `infrastructure` → `presentation`, зависимости только
внутрь. В `application/use_cases/` по файлу на сценарий: класс с `__call__`, зависимости —
порты из `application/ports.py` через конструктор. Composition root — `presentation/api/container.py`.

Границы проверяет `import-linter` в pre-commit и CI; домену и application запрещено
импортировать FastAPI, asyncpg, pydantic, jwt, argon2, Pillow.

## Рассмотренные варианты
- **Слоистый «роутер → сервис → репозиторий»** — проще, но сервисы быстро становятся
  свалкой методов, а правила смешиваются с доступом к данным.
- **Hexagonal с шиной команд** — лишняя церемония для 30 сценариев.

## Последствия
- Use case'ы тестируются на in-memory фейках (`tests/fakes.py`) — без базы, за миллисекунды.
- Больше файлов: 30+ коротких модулей. Это осознанно — сценарий находится по имени файла.
- Фейки нужно поддерживать вместе с портами; расхождение ловят интеграционные тесты.
