# Как вносить изменения

Правила короткие, и почти каждое проверяется автоматически — в таблице в конце видно, чем.
Если правило мешает — предложите изменить его через PR в этот файл, а не обходите.

## 1. Подготовка

```bash
cd backend
make install        # uv sync + pre-commit хуки (pre-commit и commit-msg)
```

Хуки запускают ruff, mypy, import-linter и юнит-тесты на каждый коммит и проверяют формат
сообщения. `--no-verify` не используем: CI всё равно проверит то же самое.

## 2. Цикл работы — TDD

Каждое изменение поведения начинается с теста, который падает.

1. **Red.** Напишите тест на сценарий и убедитесь, что он падает *по правильной причине*
   (нет функции, неверный результат), а не из-за опечатки.
2. **Green.** Минимальный код, чтобы тест прошёл.
3. **Refactor.** Уберите дублирование, тесты остаются зелёными.

Какой тест писать первым:

| Что меняете | Первый тест | Где |
|-------------|-------------|-----|
| Правило предметной области (статусы, валидация) | юнит на сущность | `tests/unit/domain/` |
| Новый сценарий | юнит на use case с фейками | `tests/unit/application/` |
| SQL-запрос или схему | интеграционный | `tests/integration/` |
| HTTP-контракт | e2e-сценарий | `tests/e2e/` |

Красное состояние не коммитим — хук прогоняет юнит-тесты. Поэтому тест и код попадают
в **один** коммит, и на ревью тест видно рядом с кодом. Багфикс начинается с теста,
который воспроизводит баг.

## 3. Архитектура: правила слоёв

```
presentation → infrastructure → application → domain
```

- **domain** не импортирует ничего из проекта и никаких фреймворков (FastAPI, asyncpg, pydantic).
- **application** знает только domain и свои порты (`ports.py`). Никакого SQL и HTTP.
- **infrastructure** реализует порты: SQL на asyncpg, argon2, JWT, файлы.
- **presentation** — тонкий слой: разобрать запрос → вызвать use case → вернуть ответ.
  Бизнес-логики в роутерах нет.

Нарушение границ ломает `make arch` (import-linter) — и коммит, и CI.

### Новый сценарий — чек-лист

1. Тест в `tests/unit/application/` (на `tests/fakes.py`).
2. Файл `application/use_cases/<глагол>_<объект>.py`, один класс с `__call__`, докстринг
   «Сценарий: …». Один сценарий — один use case, даже если он короткий.
3. Если нужен новый доступ к данным — метод в порт (`ports.py`), реализация в
   `infrastructure/db/`, интеграционный тест, метод в фейке.
4. Роут в `presentation/api/routes/`, e2e-тест.
5. Строка в [docs/use-cases.md](docs/use-cases.md).

### SQL и миграции

- Только нативный SQL через asyncpg, значения — **только** параметрами `$1..$N`.
  Склеивать в запрос можно лишь константы модуля.
- Схема меняется **новым** файлом `infrastructure/db/migrations/NNNN_что_делает.sql`.
  Применённые миграции не редактируем никогда.
- Инварианты, которые можно выразить в БД (enum, CHECK, UNIQUE), выражаем и там, и в домене.

### Фронтенд

- Next.js 16 отличается от того, что вы помните: перед изменением роутинга, кеша или метаданных
  прочитайте раздел в `frontend/node_modules/next/dist/docs/` (см. `frontend/AGENTS.md`).
- Логика — в `src/lib` и тестируется Vitest первой (TDD так же, как на бэкенде): API-клиент,
  форматирование дат, хуки. Компоненты с поведением (форма, модерация, карточка) — тест на
  Testing Library по ролям и подписям, а не по классам.
- Цвета — только токены из `globals.css`. Новый токен или скин → тест `contrast.test.ts`
  проверит WCAG сам.
- Новый экран или сценарий → e2e в `frontend/e2e/` с `expectAccessible(page, …)` (axe).
- Только нативные `<button>` / `<a>`, у каждого поля `<label>`, цели не меньше 44×44.

E2E локально:

```bash
docker compose up -d db
cd backend && STUDLENTA_ROOT_PATH=/studlenta STUDLENTA_SECURE_COOKIES=false make run   # :8000
cd frontend && npm run build && cp -r public .next/standalone/ && cp -r .next/static .next/standalone/.next/
PORT=3000 API_INTERNAL_URL=http://localhost:8000 node .next/standalone/server.js        # :3000
DATABASE_URL=… npm run e2e   # глобальная подготовка создаёт модератора через CLI бэкенда
```

## 4. Стиль

- Python 3.13, ruff (format + lint), mypy `--strict`. Строка ≤ 100 символов.
- Имена кода — по-английски, тексты для пользователя и комментарии — по-русски.
- Комментарий объясняет *почему*, а не *что*.
- Ошибки для пользователя — через исключения домена (`ValidationError` с полями и т. д.);
  presentation сам превращает их в HTTP-коды.

## 5. Коммиты и ветки

Ветка от `main`: `feat/moderation-history`, `fix/calendar-timezone`.

Сообщение — [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
тип(область): что сделано в повелительном наклонении

Зачем — если неочевидно.
```

Типы: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `build`, `ci`, `perf`, `style`,
`revert`. Области: `domain`, `feed`, `moderation`, `auth`, `author`, `api`, `db`, `deploy`, `web`.

## 6. Pull request

- Маленький и про одно. Заполните шаблон: что, как проверено, нужен ли ADR.
- Значимое решение (новая зависимость, смена подхода, отказ от фичи) — новый ADR в `docs/adr/`.
- Мёрж только при зелёном CI. После мёржа в `main` CI сам выкатывает прод.

## 7. Определение «готово»

- [ ] Тест написан до кода; все тесты зелёные, покрытие ≥ 90 %
- [ ] `make check` проходит
- [ ] Сценарий есть в `docs/use-cases.md`, решение — в ADR (если было)
- [ ] Тексты интерфейса и ошибок понятны студенту, без кодов и стектрейсов

## Что проверяется автоматически

| Правило | Pre-commit | CI |
|---------|:---------:|:--:|
| Стиль (ruff format / lint, включая bandit-правила S) | ✓ | ✓ |
| Фронтенд: eslint, tsc, Vitest (вкл. контраст токенов) | ✓ | ✓ |
| Фронтенд: Playwright + axe (WCAG 2.1 AA) на полном стеке | — | ✓ |
| Типы (mypy --strict) | ✓ | ✓ |
| Границы слоёв (import-linter) | ✓ | ✓ |
| Юнит-тесты | ✓ | ✓ |
| Интеграционные и e2e на PostgreSQL 16 | — | ✓ |
| Покрытие ≥ 90 % | — | ✓ |
| Формат сообщения коммита | ✓ (commit-msg) | ✓ (все коммиты PR) |
| Деплой только из `main` после всех проверок | — | ✓ |

TDD-порядок и «один сценарий — один use case» автоматически не проверить — их смотрим на ревью.
